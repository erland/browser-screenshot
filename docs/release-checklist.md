# Release checklist – Browser Screenshot

This checklist is for deciding whether a published image is ready to deploy to production. It does **not** block GitHub Actions from building the image for a GitHub Release.

## Source and documentation

- [ ] Canonical source verification passed for the release commit (`npm ci`, lint, typecheck, unit tests, build).
- [ ] Functional, architecture, security and deployment documentation matches the release.
- [ ] No secrets, tokens, cookies, database credentials or private keys are committed.

## Container and image

- [ ] `./scripts/verify-container.sh` passed using the production Dockerfile.
- [ ] Chromium starts as non-root with sandbox required.
- [ ] `/health` and PostgreSQL-backed `/ready` pass.
- [ ] The release image contains both `linux/amd64` and `linux/arm64` manifests.
- [ ] Provenance and SBOM were generated by the release workflow.
- [ ] The exact immutable version or digest selected for deployment is recorded.

## Acceptance and security

- [ ] `./scripts/verify-acceptance.sh` passed against a representative HTTPS deployment when required.
- [ ] Desktop and mobile UI acceptance passed when required.
- [ ] Anonymous/unauthorized access is denied.
- [ ] Loopback/private destination negative cases are blocked.
- [ ] Production egress policy has been checked for the target environment.

## Operations

- [ ] PostgreSQL backup/restore expectations are understood.
- [ ] Rollback version is known.
- [ ] Required runtime secrets are configured.
- [ ] Logging/retention and basic operational monitoring are configured.
- [ ] `docs/operations-runbook.md` is available to the operator.

## Optional formal GO/NO-GO gate

For releases that require the stricter evidence-based decision, the existing helper can still be run manually:

```bash
npm run release:gate
```

It remains fail-closed and expects the evidence described by the script. The GitHub Release workflow no longer downloads or requires `release-evidence.tar.gz`.

## Tag semantics

- Stable release `v1.2.3`: publishes `1.2.3`, `v1.2.3` and `latest`.
- Prerelease `v1.2.3-rc.1`: publishes prerelease version/tag only; `latest` is unchanged.
- Production Coolify deployments should preferably use an immutable version tag rather than `latest`.
